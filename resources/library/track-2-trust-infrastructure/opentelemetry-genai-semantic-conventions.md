# OpenTelemetry Gen AI Attribute Registry
**Org:** OpenTelemetry (Cloud Native Computing Foundation project)
**Source:** opentelemetry.io, semantic conventions documentation
**URL:** https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/
**Accessed:** 2026-11-14
**Type:** technical standard

## Summary

This page is the attribute registry for the `gen_ai.*` namespace within OpenTelemetry's semantic conventions, a set of standardized names, types, and descriptions for telemetry attributes used to instrument generative AI systems. The page notes that most of the attributes it lists have "moved" and are marked deprecated in favor of a separate OpenTelemetry GenAI semantic conventions repository, so the page functions largely as a legacy/transitional reference rather than the current living specification. The attributes cover model requests and responses, token usage, agents, tools, retrieval, embeddings, and evaluation, intended to let telemetry from different GenAI frameworks and providers be correlated using a common vocabulary.

## Key Claims / Findings

- The registry defines attribute groups for: **agent** identity (`gen_ai.agent.id`, `.name`, `.description`, `.version`), **conversation/workflow** tracking (`gen_ai.conversation.id`, `gen_ai.workflow.name`), **data source and retrieval** (`gen_ai.data_source.id`, `gen_ai.retrieval.documents`, `gen_ai.retrieval.query.text`), **embeddings** (`gen_ai.embeddings.dimension.count`, `gen_ai.request.encoding_formats`), **evaluation** (`gen_ai.evaluation.name`, `.score.value`, `.score.label`, `.explanation`), **messages/instructions** (`gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`), **operation metadata** (`gen_ai.operation.name` with well-known values `chat`, `create_agent`, `embeddings`, `execute_tool`, `generate_content`, `invoke_agent`, `invoke_workflow`, `retrieval`, `text_completion`; `gen_ai.output.type`), **provider identity** (`gen_ai.provider.name`, with well-known values including `anthropic`, `openai`, `aws.bedrock`, `gcp.vertex_ai`, `mistral_ai`, `cohere`, `x_ai`, among others), **request parameters** (`gen_ai.request.model`, `.temperature`, `.top_p`, `.top_k`, `.max_tokens`, `.frequency_penalty`, `.presence_penalty`, `.seed`, `.stop_sequences`, `.choice.count`, `.stream`), **response data** (`gen_ai.response.id`, `.model`, `.finish_reasons`, `.time_to_first_chunk`), **tool use** (`gen_ai.tool.name`, `.description`, `.type`, `.call.id`, `.call.arguments`, `.call.result`, `.definitions`), and **token usage** (`gen_ai.usage.input_tokens`, `.output_tokens`, `.cache_creation.input_tokens`, `.cache_read.input_tokens`, `.reasoning.output_tokens`, `gen_ai.token.type`).
- A set of older attributes is explicitly marked deprecated with named replacements, for example: `gen_ai.system` replaced by `gen_ai.provider.name`; `gen_ai.usage.prompt_tokens` replaced by `gen_ai.usage.input_tokens`; `gen_ai.usage.completion_tokens` replaced by `gen_ai.usage.output_tokens`; and `gen_ai.completion` / `gen_ai.prompt` removed entirely, with the Event API recommended for recording actual content instead of span attributes.
- Cached and reasoning tokens are accounted for as subsets of the main totals: cache-related token counts "are included in input tokens," and reasoning-output tokens "are included in output tokens," rather than being additive separate figures.
- The registry explicitly flags several attributes as carrying potentially sensitive data: input/output messages, system instructions, retrieval query text, and tool call arguments/results may contain PII, and the spec calls out structured recording (events, not ad hoc strings) as the preferred form.
- The underlying problem this registry addresses is standardization: without a shared vocabulary, telemetry emitted by different GenAI frameworks, SDKs, and model providers (e.g., OpenAI-specific vs. Anthropic-specific fields) cannot be correlated, aggregated, or queried uniformly across observability backends. The provider-name field is described as "a best-effort discriminator" that "may differ from the actual model host," indicating the standard does not guarantee perfect attribution to the underlying infrastructure.
- Most of the page's content is under a "Moved" deprecation notice, meaning the authoritative, current version of these conventions lives in a separate OpenTelemetry GenAI semantic conventions repository rather than on this registry page itself; this page's well-known-value tables are still marked at "development" stability.

## Relevance to the sprint

These conventions define what a standardized, machine-readable AI action log entry should contain at minimum (operation type, provider/model identity, inputs/outputs, token accounting, tool calls) and this is directly useful as a schema baseline for a tamper-evident action recorder: hashing or signing a log entry only produces a meaningful integrity guarantee if the entry's fields are well-defined and comparable across systems, and this registry supplies that shared field vocabulary (e.g., `gen_ai.tool.call.id`, `gen_ai.tool.call.arguments`, `gen_ai.response.id`) rather than requiring the project to invent its own schema from scratch. However, the standard itself says nothing about integrity, signing, or tamper-evidence; it is a naming/structure convention for observability telemetry, not a trust or provenance mechanism, so any tamper-evident layer (hashing, signatures, append-only logging) would need to be built on top of these fields rather than being provided by the spec.
